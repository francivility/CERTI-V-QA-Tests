8. HYPOTHESIS UNDER TEST (from the test brief)
------------------------------------------------------------------------------
  Dashboard response degradation and query bottlenecks under concurrent staff
  logins due to the total absence of a quick-access in-memory cache layer
  (like Redis) for recurrently loaded view arrays.

Status: NOT OBSERVED and NOT MEASURABLE yet. The absence of a cache is a fact;
        its effect is unproven.

Evidence from the backend source:
- Consistent as a fact: there is no cache layer. settings.py defines no
  CACHES, requirements.txt has no Redis or Memcached client, and no view uses
  the cache API. Every queue read is recomputed.

- What each read costs: the receiving and CTDO queues serialize every pending
  application with all of its documents, unpaginated
  (applications/views.py:501-503, :808-810). The payment and legal queues load
  related rows per application.

- Not shown to be the cause of anything: no queue query executed in this run.
  Whether caching matters depends on queue sizes, and pagination plus
  select_related would reduce the same cost without adding a service.

- A cache would not help login. The cost of a working staff-login is the
  password hash check, which is CPU-bound by design.

- Separate defect, confirmed in isolation: the role check does not enforce
  roles. HasRole reads required_role from the DRF view instance
  (core/permissions.py:9), but the views assign it to the function object
  inside the view body (for example applications/views.py:500), which the
  instance never sees. Running this project's HasRole against a view written
  the same way returned required_role = None and has_permission = True. Only
  four legal views are also patched through .cls (legal/views.py:1602-1605).
  If this holds end to end, any logged-in account, including an applicant,
  passes the role check on the other staff endpoints. It could not be
  confirmed against the running server because no login works.
