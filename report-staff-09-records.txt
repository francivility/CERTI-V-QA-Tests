(`python manage.py showmigrations`, run against the same backend checkout the
server on :8000 was started from):

That is 3 of 54 project migrations applied. Tables and columns the current
models expect do not exist, so PostgreSQL rejects the queries and Django
answers 500 (ProgrammingError). This is a deployment/setup defect, not a
capacity limit: the same 500s were reproduced with a single curl request
before any load was applied.

8. HYPOTHESIS UNDER TEST (from the test brief)
------------------------------------------------------------------------------
  Application server timeout dropouts caused by unoptimized date checking
  loops evaluating large datasets without table partitioning or indexing on
  certificate dates.

Status: NOT OBSERVED and NOT MEASURABLE yet. The missing index is real; the
        loop is not.

Evidence from the backend source:
- Consistent: StatementOfAccount.expiry_date is a DateField with no index
  (payments/models.py:24), and Application.status is not indexed either.
  expiry_monitor filters on both (records/views.py:136-139).

- Contradicted: there is no date-checking loop. The window is a single SQL
  range filter with select_related; Python only formats the rows returned
  (records/views.py:142-148).

- Unbounded: the result is not paginated, and ?days accepts any integer, so a
  large window returns every approved certificate.

- Related: reports_summary runs about eight COUNT and GROUP BY queries per
  request (records/views.py:165-187), with no cache.

- Not measurable: the tables are absent. Partitioning addresses volumes far
  beyond anything shown here; an index on expiry_date is the proportionate
  first step, checked with EXPLAIN ANALYZE on seeded data.
