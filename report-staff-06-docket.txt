8. HYPOTHESIS UNDER TEST (from the test brief)
------------------------------------------------------------------------------
  Connection pooling exhaustion at the server level due to massive SQL joins
  pulling historical data from multiple tables simultaneously, causing
  subsequent requests to time out.

Status: NOT OBSERVED and NOT EXERCISED. Contradicted by the code.

Evidence from the backend source:
- Contradicted: there is no connection pool to exhaust. settings.py configures
  a plain PostgreSQL connection with no pooler and no CONN_MAX_AGE, so Django
  opens one connection per request thread and closes it afterwards. The limit
  that could be reached is PostgreSQL's max_connections, under many
  simultaneous threads.

- Contradicted: neither endpoint performs a large join. paid_queue filters
  applications by status and payment state (payments/views.py:704-708);
  generate_docket loads one application.

- Real costs in the code: paid_queue loads the profile, CPC type, payment and
  SOA per row, unpaginated (views.py:709-719). generate_docket_number counts
  dockets with a substring match on "-<year>-", which scans the applications
  table on every call (payments/utils.py:46-49).

- Real concurrency risk: the docket number comes from that count plus an
  existence check, with no lock and no unique constraint on docket_number
  (applications/models.py:57). Two cases docketed at the same instant can
  receive the same number. The code comment acknowledges the race; the check
  narrows it but does not close it.
