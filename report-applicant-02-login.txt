6. FAILURE NARRATIVE - WHAT ACTUALLY FAILED
------------------------------------------------------------------------------
POST /accounts/login/ returned 500 on all 182 attempts: "ProgrammingError:
column accounts_user.contact_no_2 does not exist". The User model has a
contact_no_2 field (migration accounts.0012, unapplied), so the very first
SELECT against accounts_user is rejected. The failure is identical for a
username that does not exist, so it is independent of the test account.

With no access token, the five authenticated endpoints answered 401, and token
refresh answered 400 ("refresh: This field may not be null") because there was
no refresh token to send. These are consequences of the login failure. POST
/accounts/google/ answered 400 as expected (Google sign-in is not configured),
which is the only genuine pass.

Failing logins averaged 933 ms (p95 1.74 s) at 20 VUs against about 100 ms at
1 VU, most likely the cost of rendering the DEBUG traceback page on every
request.

That is 3 of 54 project migrations applied. Tables and columns the current

capacity limit: the same 500s were reproduced with a single curl request
before any load was applied.

8. HYPOTHESIS UNDER TEST (from the test brief)
------------------------------------------------------------------------------
  Exclusive database table write-locks caused by cascading delete operations
  across deep foreign key mappings during account deletion, blocking all
  concurrent authentication tokens.

Status: NOT OBSERVED and NOT EXERCISED. The code does not support the stated
        mechanism.

Evidence from the backend source:
- Not exercised: this script sends delete-account with a deliberately wrong
  password. All VUs share one test account, and new accounts cannot be created
  through the API without passing face/ID verification, so a real delete would
  remove the account every other VU is using.

- Contradicted: delete_account calls user.delete() (accounts/views.py:1059).
  PostgreSQL DELETE takes row-level locks, not exclusive table locks, and
  login is a plain SELECT that row locks do not block.

- Separate defect found by reading the code: Application.applicant_profile is
  on_delete=PROTECT (applications/models.py:46). Deleting an account that has
  any application raises ProtectedError, which the view does not catch, so the
  expected result is a 500, not a cascade. The view's docstring ("Cascades to
  the applicant's applications") is wrong. This was not executed and should be
  confirmed with a disposable account.
