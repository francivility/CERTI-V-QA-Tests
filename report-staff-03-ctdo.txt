8. HYPOTHESIS UNDER TEST (from the test brief)
------------------------------------------------------------------------------
  Operational database locking caused by intensive real-time mathematical
  aggregation loops (COUNT, SUM, AVG) running continuously on the main
  application transactional tables without a caching layer.

Status: NOT OBSERVED and NOT EXERCISED. Half supported by the code: no cache,
        but no locking either.

Evidence from the backend source:
- Consistent: ctdo_reports recomputes everything on each request, about eight
  COUNT / GROUP BY queries over the applications and decision tables
  (legal/views.py:1453-1500). There is no cache: settings.py defines no CACHES
  and nothing in the code calls the cache API.

- Contradicted: these are read-only aggregates (COUNT with GROUP BY; no SUM or
  AVG on this endpoint). Under PostgreSQL's MVCC they do not block inserts or
  updates on the same tables. The cost is repeated CPU and I/O per request,
  not locking.

- Not measurable: the tables are absent, and the cost depends on row counts.

- Related: ctdo_history joins the status log, applies DISTINCT and then loads
  the profile and CPC type per row (applications/views.py:819-831),
  unpaginated.

- Separate defect from reading the code: ctdo_decision moves any application
  to pending_assessment or needs_correction without checking that it is
  currently pending_ctdo (applications/views.py:879-895).
