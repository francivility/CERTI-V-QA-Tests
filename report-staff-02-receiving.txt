6. FAILURE NARRATIVE - WHAT ACTUALLY FAILED
------------------------------------------------------------------------------
The setup login failed (500, missing column accounts_user.contact_no_2). All
eight endpoints require a token, so each of the 396 iterations received 401 on
every call, including case-search. A 401 is issued before any view code or SQL
runs, so the 1.5 to 2.6 ms averages describe the authentication layer only.

7. ROOT CAUSE OBSERVED IN THIS RUN
------------------------------------------------------------------------------
The database behind the running server is far behind the code. Read-only check
(`python manage.py showmigrations`, run against the same backend checkout the
server on :8000 was started from):

  app            applied / total

  applications      0 / 16

That is 3 of 54 project migrations applied. Tables and columns the current
models expect do not exist, so PostgreSQL rejects the queries and Django
answers 500 (ProgrammingError). This is a deployment/setup defect, not a
capacity limit: the same 500s were reproduced with a single curl request
before any load was applied.

8. HYPOTHESIS UNDER TEST (from the test brief)
------------------------------------------------------------------------------
  Database lockups and memory utilization spikes caused by complex, unindexed
  text matching searches (LIKE %term%) running simultaneously across millions
  of relational rows.

Status: NOT OBSERVED and NOT MEASURABLE yet. The query shape is as described;
        the consequences are not supported.

Evidence from the backend source:
- Consistent: case_search filters with icontains on case_number, docket_number
  and the applicant's business_name (applications/views.py:726-730). That is
  ILIKE '%term%', which an ordinary index cannot serve, so each search scans
  the table.

- Consistent: each result row then triggers further lookups for the applicant
  profile, CPC type, release and decision (views.py:738-746), up to 50 rows
  per search.

- Contradicted: a SELECT does not lock other readers or writers in PostgreSQL,
  so slow searches would raise latency and CPU, not cause lockups. Results are
  capped at 50, which bounds memory.

- Not measurable: the applications table does not exist in this database.
  "Millions of rows" is an assumption about volume, not something this run can
  show.

- Separate defect from reading the code: forward_to_ctdo sets any application
  to pending_ctdo without checking its current status
  (applications/views.py:534-545).

- Separate defect, confirmed in isolation: the role check does not enforce
  roles. HasRole reads required_role from the DRF view instance
  (core/permissions.py:9), but the views assign it to the function object
  inside the view body (for example applications/views.py:500), which the
  instance never sees. Running this project's HasRole against a view written
  the same way returned required_role = None and has_permission = True. Only
  four legal views are also patched through .cls (legal/views.py:1602-1605).
  If this holds end to end, any logged-in account, including an applicant,
  passes the role check on the other staff endpoints. It could not be
  confirmed against the running server because no login works.
