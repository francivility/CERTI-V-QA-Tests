6. FAILURE NARRATIVE - WHAT ACTUALLY FAILED
------------------------------------------------------------------------------
The setup login failed (500, missing column accounts_user.contact_no_2), so
POST /verification/session/ answered 403 and the session poll 401.

The remaining five endpoints need no login and failed on their own: POST
/verification/submit/<code>/ returned 500 because relation
"verification_verificationsession" does not exist, and all four
/applications/qr-bridge/ endpoints returned 500 because relation
"applications_qrbridgeupload" does not exist. Neither table has been created
(verification.0001 and applications.0010 are unapplied).

The upload was the slowest call: 1.9 s average, 2.9 s p95, 3.3 s max.
qr_bridge_upload receives the 353 KB JPEG and runs prepare_image() on it
(applications/views.py:1094) before its first database statement, so real
image processing ran on every call and the request then failed at the DELETE
on the missing table. Server CPU time rose from 289 s before this script to
396 s after script 04 (the sample between the two was missed), against about
22 s for each of scripts 01 and 02. That suggests CPU-bound image work rather
than storage, but it is not isolated to this script.

answers 500 (ProgrammingError). This is a deployment/setup defect, not a
capacity limit: the same 500s were reproduced with a single curl request
before any load was applied.

8. HYPOTHESIS UNDER TEST (from the test brief)
------------------------------------------------------------------------------
  Storage disk I/O saturation resulting from writing heavy binary image
  uploads directly to local application disk drives, which starves the server
  threads processing the laptop polling loop.

Status: NOT OBSERVED. Contradicted by the code for the QR bridge.

Evidence from the backend source:
- Contradicted: QrBridgeUpload.image is a BinaryField
  (applications/models.py:164). Bridge images are stored as rows in
  PostgreSQL, and downloads are served from the row through an in-memory
  buffer (applications/views.py:1135). Nothing is written to the application's
  local disk on this path.

- Not measured: no disk counters were collected, so this run can neither
  confirm nor rule out I/O pressure on the database host.

- Real risks visible in the code: every laptop poll (qr_bridge_pending,
  views.py:1119) issues a DELETE as well as a SELECT, so the polling loop
  writes on every request; uploads are held fully in memory (up to the 20 MB
  limit in settings.py) and re-encoded on the request thread; verification
  submit reads every selfie frame into memory (verification/views.py:156).

- For local-disk writes, see the draft document upload in script 04, which
  does use a FileField under MEDIA_ROOT.
