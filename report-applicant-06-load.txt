6. FAILURE NARRATIVE - WHAT ACTUALLY FAILED
------------------------------------------------------------------------------
The setup login failed (500, missing column accounts_user.contact_no_2), so
the five authenticated routes each returned 401 on all 100 hits:
/accounts/account/, /applications/mine/, /applications/drafts/,
/applications/notifications/ and /payments/my-payments/. A 401 is issued
before any view code or SQL runs, so their latency figures do not describe
read performance.

GET /cpc-types/ is public and returned 200 on all 100 hits, with 91 ms average
and 142 ms p95. That is the only real read measured, and it was against an
empty table.

7. ROOT CAUSE OBSERVED IN THIS RUN
------------------------------------------------------------------------------
The database behind the running server is far behind the code. Read-only check
(`python manage.py showmigrations`, run against the same backend checkout the
server on :8000 was started from):

  app            applied / total
  accounts          2 / 12
  core              1 / 6
  applications      0 / 16
  payments          0 / 9
  legal             0 / 9
  records           0 / 1
  verification      0 / 1
  sessions, admin   0 / 4

That is 3 of 54 project migrations applied. Tables and columns the current
models expect do not exist, so PostgreSQL rejects the queries and Django
answers 500 (ProgrammingError). This is a deployment/setup defect, not a
capacity limit: the same 500s were reproduced with a single curl request
before any load was applied.

8. HYPOTHESIS UNDER TEST (from the test brief)
------------------------------------------------------------------------------
  Severe read query degradation and transaction queues piling up due to a
  total lack of database indexes on core user tracking columns, forcing slow
  full-table scans.

Status: NOT OBSERVED and NOT MEASURABLE yet. "Total lack of indexes" is
        contradicted by the models.

Evidence from the backend source:
- Contradicted: the six routes filter on foreign keys (applicant_profile,
  user) and Django creates an index on every ForeignKey and OneToOneField
  automatically. username is unique and therefore indexed.

- Not measurable: most of the tables behind these routes do not exist in this
  database, and the ones that do are empty. Index effects only show at
  realistic row counts.

- Columns that are filtered without an index, worth checking once data exists:
  Application.status (scanned by mark_overdue_applications on every payments
  read), Notification.is_read and Notification.title (counted on every
  notifications read), and the case-insensitive email lookups (email__iexact),
  which a plain b-tree index cannot serve.

- To confirm or reject: seed a realistic volume, then run EXPLAIN ANALYZE on
  the queries behind these routes and compare with this script's per-endpoint
  latency.
