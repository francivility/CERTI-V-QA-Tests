6. FAILURE NARRATIVE - WHAT ACTUALLY FAILED
------------------------------------------------------------------------------
POST /accounts/register/step1/ returned 500 on all 176 attempts:
"ProgrammingError: column accounts_pendingregistration.email_verified does not
exist". The view fails while looking up an existing pending registration for
the email (accounts/views.py:142), which is before the password is hashed
(line 186) and before any email is sent. Password hashing and mail delivery
therefore never executed in this run.

Everything after step1 failed as a consequence, not independently: with no
staging token the four token-protected endpoints answered 403 ("Authentication
credentials were not provided"), and the status poll answered 404
("Registration not found") for the placeholder code. The one passing check
(step2 -> 403) passed for the wrong reason: it expects 403 for an unverified
email and received 403 for a missing token.

The failing step1 calls averaged 989 ms (p95 2.0 s). A comparable 500 (login)
took about 100 ms at 1 VU. With DEBUG=True each 500 renders a full Django
traceback page (167 KB measured for the login error), which is the likely
source of that latency; it is not evidence of how a working step1 would
perform.

8. HYPOTHESIS UNDER TEST (from the test brief)
------------------------------------------------------------------------------
  CPU thread starvation due to heavy password hashing (bcrypt/argon2)
  executing on the main worker threads, combined with hanging connection loops
  waiting for synchronous SMTP email server handshakes.

Status: NOT OBSERVED in this run. Partly consistent with the code, partly
        contradicted.

Evidence from the backend source:
- Contradicted: the hasher is not bcrypt or argon2. settings.py defines no
  PASSWORD_HASHERS and neither library is in requirements.txt, so Django's
  default PBKDF2-SHA256 is used.

- Consistent: hashing is synchronous on the request thread, and step1 hashes
  twice (the password at accounts/views.py:186 and the 6-digit email code at
  accounts/email_verification.py:22).

- Consistent: send_mail() is called inline in the request
  (email_verification.py:32) with EMAIL_TIMEOUT = 15 s, so a slow SMTP server
  would hold the request for up to 15 s.

- Qualifier: the default EMAIL_BACKEND is the console backend
  (settings.py:183), which performs no SMTP handshake. The stall can only
  happen where an SMTP backend is configured through the environment.

- Not measured: none of this code ran, because step1 failed earlier.
