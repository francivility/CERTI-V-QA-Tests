server on :8000 was started from):

That is 3 of 54 project migrations applied. Tables and columns the current
models expect do not exist, so PostgreSQL rejects the queries and Django
answers 500 (ProgrammingError). This is a deployment/setup defect, not a
capacity limit: the same 500s were reproduced with a single curl request
before any load was applied.

8. HYPOTHESIS UNDER TEST (from the test brief)
------------------------------------------------------------------------------
  Server resource starvation and worker lockups due to concurrent multi-
  analyst requests compiling extensive transaction tables into live layout
  documents.

Status: NOT OBSERVED and NOT EXERCISED. Plausible from the code, with a
        different mechanism than stated.

Evidence from the backend source:
- Consistent: pos_document builds the Payment Order Slip as DOCX and converts
  it to PDF on every GET, with no stored copy reused
  (payments/views.py:334-341). send_pos does the same
  (payments/views.py:375-376).

- The expensive step is the conversion, not the data. convert_to_pdf drives
  Microsoft Word through COM via docx2pdf, writing temp files and retrying up
  to three times on file-handle errors (legal/document_generation.py:555-583).
  It runs on the request thread and needs Word installed on the server.

- Correction to the stated mechanism: the document covers one Statement of
  Account and its fee lines, not "extensive transaction tables".

- Not exercised: a 20-VU run against a working pos-document endpoint is the
  test that would confirm or reject this. It should be the first script re-run
  after the database is fixed.

- Related: control numbers are assigned from a daily count, which can collide
  when two SOAs are issued at once; the code handles this with a unique
  constraint and up to five retries (payments/views.py:197-203).
