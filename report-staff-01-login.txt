6. FAILURE NARRATIVE - WHAT ACTUALLY FAILED
------------------------------------------------------------------------------
POST /accounts/staff-login/ returned 500 on all 280 attempts:
"ProgrammingError: column accounts_user.contact_no_2 does not exist". It is
the same failure as the applicant login and happens for any username. Failing
logins averaged 340 ms (p95 919 ms).

With no token, staff-account, staff-verify-email and esignature answered 401,
and token refresh answered 400 because there was no refresh token.

Three endpoints are rate limited per IP and behaved as designed. staff-google
returned 400 five times ("not configured") and then 429 for the remaining 275
(limit 5/hour). staff-password-reset/confirm returned 400 ten times and then
429 (limit 10/hour). These are the only genuine passes. staff-password-
reset/request returned 500 on its first five calls, on the same missing
column, and 429 afterwards.

Side effect of this run: those limits are now used up for an hour from this
machine, and the "anon" limit is shared with the applicant password reset.

That is 3 of 54 project migrations applied. Tables and columns the current
models expect do not exist, so PostgreSQL rejects the queries and Django
answers 500 (ProgrammingError). This is a deployment/setup defect, not a
capacity limit: the same 500s were reproduced with a single curl request
before any load was applied.

8. HYPOTHESIS UNDER TEST (from the test brief)
------------------------------------------------------------------------------
  Network bandwidth choking and database driver delays caused by fetching and
  converting large binary data strings (BLOB fields) for electronic signatures
  directly out of primary user rows instead of object storage links.

Status: NOT OBSERVED. Contradicted by the code.

Evidence from the backend source:
- Contradicted: User.esignature is an ImageField with upload_to='esignatures/'
  (accounts/models.py:15). The image is a file under MEDIA_ROOT and the user
  row stores only its path. There is no BLOB column on the user table.

- Contradicted: GET /accounts/esignature/ returns metadata and a URL
  (has_esignature, name, uploaded_at, esignature_url;
  accounts/views.py:1180-1185). No image bytes pass through this endpoint or
  through the database driver.

- Not exercised: the endpoint answered 401 on every call.

- Real cost on this path once login works: the password hash check runs
  synchronously on every staff-login, and uploads are served by Django itself
  from /media/ (certiv_backend/urls.py), not by a web server or object
  storage.
