6. FAILURE NARRATIVE - WHAT ACTUALLY FAILED
------------------------------------------------------------------------------
The setup login failed (500, missing column accounts_user.contact_no_2). All
eleven endpoints in this script require a token, so every one of the 366
iterations received 401 on every call. Because DRF rejects an unauthenticated
request before touching the database, these responses were fast (about 9 ms
average) and say nothing about the payment code.

No view body ran in this script: not the bill builder, not the Xendit client,
not the receipt, CPC or notice lookups.

capacity limit: the same 500s were reproduced with a single curl request
before any load was applied.

8. HYPOTHESIS UNDER TEST (from the test brief)
------------------------------------------------------------------------------
  Thread pool exhaustion caused by hanging synchronous external API
  connections to the third-party payment provider (Xendit) blocking incoming
  server requests.

Status: NOT OBSERVED and NOT EXERCISED. A plausible design risk, bounded by a
        timeout.

Evidence from the backend source:
- Consistent: Xendit is called synchronously on the request thread with the
  requests library (payments/xendit_service.py:20 and :45). A slow Xendit
  holds that request for as long as the call takes.

- Qualifier: both calls set timeout=30, so a request cannot hang indefinitely.
  The exposure is 30 s per call, not unbounded.

- Qualifier: the server under test is Django's development server (response
  header "WSGIServer/0.2"), which starts a thread per request and has no fixed
  pool to exhaust. The risk applies to a production deployment with a fixed
  number of sync workers.

- Amplifier: GET /payments/<id>/xendit/status/ calls Xendit on every poll
  (payments/xendit_views.py:82), so a polling front end multiplies the
  exposure.

- Not exercised: XENDIT_SECRET_KEY defaults to empty, in which case checkout
  returns 502 without any network call.

- Related hot spot in the code: mark_overdue_applications() runs on every my-
  payments and my-bill read, and again once per application inside
  _public_bill_data (payments/views.py:927 and :1072).
